# Security Intelligence & AI Analyst (v2.0.4)

## Scope

The v2.0.4 intelligence layer enriches normalized events with a small allowlist of process, container, file-hash and network entities. It correlates incidents and context-only events, generates candidate MITRE ATT&CK labels, builds an incident timeline, and can submit a sanitized evidence summary to a configured AI deployment.

It is a **triage aid**, not attribution, proof of execution, a malware verdict, or an autonomous response system.

## Enrichment fields

Entities are extracted only from known fields:

- Process: PID, parent PID, executable name/path.
- Identity/container: username, container ID/name.
- File: path and SHA-256 (only a valid 64-character hex digest).
- Network: domain, flow ID and Zeek UID; normalized events separately retain validated source/destination IP and ports.

Command lines, request/response bodies, arbitrary osquery columns, raw source payloads, cookies, authorization values and secret match contents are not added to the AI context. Credential-like values are redacted before normalized details are persisted. Event details are bounded to 8 KiB.

## Correlation model

`POST /api/v204/security/incidents/{incident_id}/correlate` performs a bounded time-window correlation (1–240 minutes). The scorer uses explicit anchors such as:

- Same SHA-256: 0.99 candidate confidence.
- Same host/node/container and process PID: 0.96.
- Same host and file path: 0.82.
- Same domain with a shared IP endpoint: 0.88.
- Same domain alone: 0.72.
- Shared network endpoint plus same host/node: 0.74.

A common hostname alone is not enough to correlate. Scores are ranking heuristics, not statistical probabilities. Event clock drift, NAT, reused PIDs, container IDs and shared infrastructure can create false links or missed links. Analysts must inspect source evidence.

The read-only analysis endpoint computes links without persisting them. The explicit correlate endpoint persists canonical incident pairs and emits an audit event. Incident links are unique by sorted incident IDs.

## Context events and timeline

Zeek connection/DNS/HTTP/TLS/file records remain context-only unless the source adapter recognizes them as alert-like. A matched context event can appear in the incident timeline with `context_only=true`, observed time, source, title and correlation evidence. It does not create an incident by itself.

The timeline includes allowlisted host/network/process metadata. It does not contain raw PCAP, full command lines or request bodies.

## MITRE ATT&CK candidates

Technique labels are generated by conservative keyword/metadata rules. The mapping includes candidate techniques for shell/PowerShell execution, scheduled tasks, systemd services, tool transfer, web protocols, credential dumping, process injection, C2 exfiltration, autostart, system discovery and account discovery.

A mapping is a **candidate** based on telemetry text/metadata. It does not prove that a technique occurred. The absence of a candidate does not prove the technique did not occur. Review upstream event IDs, event semantics, timestamps and endpoint telemetry before using mappings as detection-coverage claims.

## AI Analyst

`POST /api/v204/security/incidents/{incident_id}/ai-analysis` requires both `ai:invoke` and `security:analysis`. The server builds a compact prompt from normalized evidence, then submits it to the existing AI job queue. A deployment can be explicitly selected; otherwise the standard local/free routing policy applies. Paid deployments still require explicit selection and existing paid-budget consent/configuration.

The AI is instructed to:

1. Separate direct observations from hypotheses.
2. Describe time ordering and correlated evidence.
3. State uncertainty, missing telemetry and alternative explanations.
4. Treat ATT&CK mappings as candidates, not proof.
5. Recommend human validation and approved defensive procedures.
6. Never execute commands or automatically change endpoint/network state.

Prompts/results follow the configured AI queue storage policy. In SQLite mode the job payload/result is process-memory only. In distributed PostgreSQL mode it uses the existing encrypted job payload mechanism. Upstream AI providers may process the prompt according to their own retention and privacy policies; do not send sensitive incidents to a cloud provider unless that transfer is authorized.

## API and RBAC

- `GET /api/v204/security/mitre/summary`: `security:analysis`.
- `GET /api/v204/security/incidents/{id}/analysis`: `security:analysis`.
- `POST /api/v204/security/incidents/{id}/correlate`: `security:correlate`.
- `POST /api/v204/security/incidents/{id}/ai-analysis`: `ai:invoke` and `security:analysis`.
- `POST /api/v204/security/ingest/{source}`: `security:ingest`.

Viewer can read the analysis; analyst/operator can persist correlations subject to their scopes; a sensor can ingest only. Existing `/api/v203/security/*` routes remain for compatibility.

## Continuous telemetry tailer

`tools/tail_jsonl.py` follows Wazuh, Suricata, Zeek, Falco and osquery JSONL files. Trivy remains on bounded batch ingestion because Trivy output is generally a report document, not a continuously appended event stream.

- Defaults to start at EOF on first start; use `--from-beginning` for intentional backfill.
- Persists file device/inode/byte offset in a mode-0600 SQLite checkpoint database under a mode-0700 parent directory.
- Uses a per-input `flock`; multiple different log files can share one checkpoint database.
- Sends batches of at most 50; defaults to 25. Offset advances only after HTTP 202 acknowledgement.
- A crash after server acknowledgement but before checkpoint commit may replay a batch; server deduplication by `(source, source_event_id)` makes this idempotent when the source supplies stable IDs.
- Follows rename rotation by draining the old file descriptor, and recovers the old inode after restart if the rotated file remains available.
- Detects many copytruncate cases by comparing file size to offset. If a rotated inode disappears before restart, it stops with an explicit error instead of silently resetting.
- Malformed lines are skipped and counted without logging their contents. An incomplete final line is held until a newline arrives.
- Remote servers require HTTPS, redirects are not followed, token files must be mode 0600 or stricter, and telemetry content is never logged by the tailer.

This is an at-least-once sender with server-side deduplication, not a transactional log broker. For loss-sensitive pipelines, prefer an upstream durable collector such as the vendor's supported agent/forwarder and monitor `telemetry-tail` service logs/checkpoint lag.

### Manual run

```bash
python3 tools/tail_jsonl.py \
  --source suricata \
  --server https://cyberforge.example.net \
  --input /var/log/suricata/eve.json \
  --token-file /etc/cyberforge-server/telemetry/suricata.token \
  --state-file /var/lib/cyberforge-telemetry/checkpoints.sqlite3
```

### systemd template

The package includes `deploy/systemd/cyberforge-security-tail@.service.example`. The installer installs the template but does not enable any sensor automatically. Create one environment file per source at `/etc/cyberforge-server/telemetry/<instance>.env`:

```ini
CF_TELEMETRY_SOURCE=suricata
CF_SERVER_URL=https://cyberforge.example.net
CF_TELEMETRY_FILE=/var/log/suricata/eve.json
CF_SENSOR_TOKEN_FILE=/etc/cyberforge-server/telemetry/suricata.token
```

The token file must be owned by `cyberforge-server` and mode `0600`. Grant the service account read access to the selected source log using a dedicated group or ACL; do not run the shipper as root merely to read logs. Then:

```bash
sudo systemctl enable --now cyberforge-security-tail@suricata.service
sudo systemctl status cyberforge-security-tail@suricata.service
sudo journalctl -u cyberforge-security-tail@suricata.service -f
```

Each instance gets a per-input lock; all can share the same checkpoint database. Use unique instance names and one config per input path.

## v2.0.4 validation notes

- Zeek JSON accepts both nested and flat dotted fields such as `id.orig_h`, `id.resp_h`, `id.orig_p` and `id.resp_p`.
- Endpoint hostnames are not treated as DNS domains. Domain anchors must come from explicit DNS query, TLS SNI/server-name or protocol-specific peer fields.
- Correlation is capped by a bounded time window and candidate count. Scores are ranking heuristics, not probabilities. A common host alone is deliberately insufficient.
- The continuous tailer-to-API path has a loopback integration test covering HTTP sensor ingestion, server-side normalization/persistence and checkpoint advancement. This does not replace validation against live source products.


## Threat Intelligence context (v2.0.5)

The incident analysis API attaches local IOC enrichment from `threat_intel.py`. Only normalized incident entities are checked against the local indicator store. Matches include source feed, confidence and severity; these are contextual matches, not proof of execution or compromise. Optional FIRST EPSS lookup is separate and user-triggered. AI messages include only this sanitized match summary and instruct the model to distinguish indicators from independently observed activity. See [Threat Intelligence Guide](THREAT_INTELLIGENCE.md).
